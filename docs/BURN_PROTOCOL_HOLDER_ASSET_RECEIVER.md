# Burn Protocol holder-controlled external asset receiver

## Classification

This transaction adds a session-only external evidence receiver to the live Rodoh World surface. It does not bundle the Burn estate, store panel bytes in the cartridge bay, append asset records to a portable run, alter the calibrated Arc, assign a Program of Record, create a Burn-specific engine path, or grant a selected file canonical standing.

The receiver is stacked on the qualified metadata-only World journey. Its authored authority remains the calibrated Arc publication:

```text

cartridge digest   cart1_870f3dfcab909fc9aace115e2c46cd30268339f80bc87a14f0eebcc4e2c28c3e
source plane       common-ship-pocket/1
exact parent       b3b299e14d8c22cde88629eb6bc4d197b8f8015eec7bf46b95f0de2a31b5f0df
```

## Receiver object

The holder opens a local folder or selects local files from a small evidence dock mounted beside the runtime. World requires one record of each format:

```text
burn-protocol-handoff-publication-activation-contract/1
burn-protocol-handoff-publication-activation-receipt/1
burn-protocol-handoff-publication-overlay/1
burn-protocol-handoff-publication-approval/1
burn-protocol-handoff-intake-receipt/1
burn-protocol-handoff-intake-contract/1
burn-protocol-corpus-asset-index/1
```

The records remain external to the Arc and run. The receiver reads them only after explicit holder selection, verifies them in the browser, creates object URLs only for individually admitted assets, and revokes those URLs on clear, reload, cartridge switch, or exit.

## Verification mechanism

The browser performs the following checks before exposing an asset:

1. Every required record has exactly one bounded JSON document with the expected format.
2. The activation receipt binds the exact activation contract, approval, and overlay bytes by SHA-256 and byte count.
3. The approval binds the intake contract, intake receipt, and asset index and passes its `approval1_` integrity digest.
4. The intake receipt and contract agree on handoff identity, parent identity, manifest counts, authority, and corpus-index counts.
5. The activation contract agrees with the approval and with the currently running cartridge id, version, Engine 1.3 version, source plane, exact parent, and computed cartridge digest.
6. A record claiming `production-exact-intake` must carry the exact reported 363,384,929-byte handoff identity and the exact v0.58.0 parent identity. A mechanism fixture cannot be relabelled as production merely by changing its evidence-tier string.
7. The overlay and activation receipt agree on the cartridge, authored boundary, custody relationship, zero runtime bundling, handoff, parent, asset-index hash, asset-index byte count, and classification counts.
8. Every selected asset must resolve unambiguously to one safe manifest path and match its indexed byte count and SHA-256.

Unindexed files are never rendered. A selected directory may contain unrelated files, but they remain ignored and are reported as such.

## Presentation boundary

The evidence dock is receiver chrome outside `ArcWorld`. It does not write a runtime extension, localStorage record, ledger entry, cartridge state, or theme scope. A verified visual receives a session object URL and an evidence card showing its classification, manifest path, digest, evidence tier, and verified-versus-indexed count.

The dock deliberately retains the authored boundary reported by the calibrated source:

```text
inherited history  read-only
live runs           counterfactual-only
story changes       none
authored panels     not-present
runtime bundling    none
```

External custody supplements the live world. It does not change authored identity and does not convert a holder-selected visual into an authored cartridge asset.

## Qualification fixture

The dedicated workflow checks out the exact Arc activation authority, rebuilds the calibrated publication, and creates a deterministic holder folder from the production activation contract. The fixture contains one valid synthetic SVG classified as a panel raster, plus a complete internally bound intake, approval, activation, overlay, and asset-index chain. It is labelled `mechanism-fixture` at every authority surface.

The workflow requires:

```text
valid holder folder                    accepted and rendered
asset changed after approval           refused
asset index changed after approval     refused
wrong cartridge digest                 refused
fixture bytes in production build      absent
external record in localStorage        absent
external record in run export          absent
external network request               absent
reload after mount                      receiver returns to idle
```

Desktop and mobile browser projects exercise the same input and verification path.

## Evidence boundary

The evidence tier is mechanism qualification. The venue is the stacked World receiver branch. The target is a future folder assembled from a passing production activation receipt and individually selected files from the exact v0.58.0 estate. The upside is that the holder can project verified visual evidence into the live world without transferring custody to the application. The downside is that the current fixture proves the receiver rather than the absent production payload. The failure mode is accepting an internally inconsistent chain, an asset changed after approval, a custody record bound to another cartridge, or a fixture presented as production evidence.

The next production transaction begins only when the exact A13C1 handoff is available and the activation bridge emits a `production-exact-intake` overlay. At that point this receiver can mount a verified subset without changing the cartridge digest or the run format.
